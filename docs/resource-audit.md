# Проверка ресурсов SFTPAddIn

Дата: 2026-10-24. Windows, x86/x64, libssh2 1.11.1, OpenSSL 3.5.2,
статические библиотеки и CRT. Проверка выполнена до коммита текущих изменений.

## Найдено и исправлено

1. **Тайм-аут закрытия SFTP-файла/каталога.** Блокирующая обёртка libssh2 может
   вернуть тайм-аут, оставив handle живым. Прежний код уже обнулял владельца;
   `sftp_shutdown` в этой версии оставшиеся handle не освобождает. Теперь общий
   механизм закрытия работает в неблокирующем режиме API и сохраняет владение
   при `EAGAIN`. После истечения времени сокет завершается, закрытие handle
   доводится до терминального результата, затем освобождаются SFTP и SSH.
   Протокольный отказ закрытия, при котором libssh2 уже освободила handle,
   отличается от незавершённого закрытия; двойного освобождения нет.
2. **Отказ выделения памяти при подготовке диагностики скачивания.** Владелец
   handle больше не обнуляется до потенциально выделяющего память `captureError`.
3. **libssh2 AES-GCM: два потерянных MAC-буфера на подключение.** По стекам
   Debug CRT выделения находились в `curve25519_sha256`, при derivation ключей
   MAC направлений E/F. Для интегрированной аутентификации AES-GCM stub не
   использовал ключ, но не разрешал вызывающему коду его освободить. Исправлено
   через `free_key = 1`. Наблюдавшийся рост был 96 байт на сессию при Curve25519.
4. **libssh2/OpenSSL 3 ECDH.** Добавлено освобождение `BN_CTX`, контекста импорта
   открытого ключа и собственной ссылки на импортированный `EVP_PKEY`.
   Изменения зависимости находятся в `ports/libssh2/resource-fixes.patch`,
   применяются автоматически локальным overlay vcpkg при сборке.
5. **OpenSSL на новых потоках Windows.** При статической линковке библиотека
   не получает `DLL_THREAD_DETACH`; без явной очистки данные завершённых потоков
   оставались в памяти. Добавлен RAII-вызов `OPENSSL_thread_stop()` при выходе
   из каждого публичного вызова клиента. Это поддерживает последовательные
   вызовы одного экземпляра с разных рабочих потоков без ожидания уничтожения
   экземпляра. Контексты живых SSH-сессий при этом не уничтожаются.
   Основание: [OpenSSL, раздел NOTES](https://docs.openssl.org/3.5/man3/OPENSSL_init_crypto/#notes).
6. **Синхронизация Native API.** `Done`, работа с менеджером памяти и обработчики
   ошибок используют тот же mutex, что и операции. Буферы предыдущей диагностики
   освобождаются при её очистке, включая ёмкость большого JSON пачки.

Владельцы файловых дескрипторов и временных файлов не копируются. Передача имени
успешно созданного временного файла RAII-владельцу выполняется перемещением,
чтобы дополнительное выделение памяти не оставило файл без очистки.

## Динамические проверки

| Проверка | x86 | x64 |
| --- | --- | --- |
| Native API: 1000 циклов, 8000 отказов выделения, ноль незавершённых выделений менеджера 1С между операциями | Пройдена | Пройдена |
| Native API с сетью: 750 строк/Blob как процедуры и 750 отказов выделения результата | Пройдена | Пройдена |
| Debug CRT: 86 циклов работы, включая 20 новых потоков и 12 задержанных закрытий | 0 блоков / 0 байт роста | 0 блоков / 0 байт роста |
| Windows handles до/после основной серии | 116 → 116 | 98 → 98 |
| Принудительный ECDH P-256/P-384/P-521 и DH group14 SHA-256: по 30 циклов каждого | 0 блоков / 0 байт роста | 0 блоков / 0 байт роста |

В циклах выполняются перечисление, Stat, скачивание в память и на диск,
отправка и замена файла, отказ доступа, неправильный пароль и отпечаток,
переподключение, явный Disconnect и уничтожение с открытой сессией.
Задержки закрытия проверяются для скачанного файла, отправленного файла и
каталога. Дополнительно проверен протокольный отказ закрытия без потери сессии.

Debug CRT измеряется после прогрева в отдельном исполняемом файле, где ядро
компоненты, libssh2 и OpenSSL используют один `/MTd` CRT. Это позволяет учитывать
их живые выделения, которые не видны из CRT внешнего EXE при загрузке DLL с `/MT`.
Память результатов Native API проверяется отдельно через учёт `IMemoryManager`.
Рост выделений и дескрипторов в перечисленных сценариях после исправлений
не обнаружен. Это конечные стресс-серии, а не доказательство отсутствия ошибок
при любом поведении сервера или многочасовой работе настоящего `rphost`.

## Повторение

```powershell
cmake --preset windows-x64
cmake --build build/windows-x64 --config Debug --target resource_stress
.\.venv\Scripts\python.exe tests/resource_stress.py build/windows-x64/Debug/resource_stress.exe
.\.venv\Scripts\python.exe tests/resource_stress.py build/windows-x64/Debug/resource_stress.exe --kex ecdh-sha2-nistp256 --cycles 10 --faults 0
.\.venv\Scripts\python.exe tests/resource_stress.py build/windows-x64/Debug/resource_stress.exe --kex ecdh-sha2-nistp384 --cycles 10 --faults 0
.\.venv\Scripts\python.exe tests/resource_stress.py build/windows-x64/Debug/resource_stress.exe --kex ecdh-sha2-nistp521 --cycles 10 --faults 0
.\.venv\Scripts\python.exe tests/resource_stress.py build/windows-x64/Debug/resource_stress.exe --kex diffie-hellman-group14-sha256 --cycles 10 --faults 0
```

Для x86 заменить `windows-x64` на `windows-x86`. Учёт Native API выполняется
в `native_host` при обычном запуске CTest и `tests/integration.py`.
